## 执行摘要 (Executive Summary)

Invoice Hub 诞生之初旨在解决普通员工在深夜个人报销整理过程中的“发票收集繁杂、手工录入易错、证明材料零散”以及企业财务端“假票重报、税号错误、附件脱节、手工对账繁重”的双重断点。在经历了 v0.1.x 的快速迭代后，系统已建立起本地邮箱同步、PDF 结构化解析、SQLite 本地存储、PySide6 桌面工作台及基础 Excel 台账导出的全链路骨架。

以下问题清单是 2026-10-04 初始走查时的观察，不代表当前代码状态：
1. **报销体验摩擦点密集**：业务“事由”字段在数据模型、交互界面与导出台账中全链路缺位；无票号票据（如出租车机打票、行程单、定额发票）查重失效，导致同日多张真票误报或重复照片误放行；移动端扫码在企业内网 AP 隔离下超时无诊断；长列表审核缺乏单键流转，操作枯燥且极易视觉疲劳。
2. **界面布局刚性与视觉退化**：工作台审核面板硬编码死锁在 420px，导致发票原件扫描件在主流 1080p 笔记本屏幕上严重受挤；正文字体降级为 12px，中文笔画粘连；状态 Badge 仅凭马卡龙浅色块区分，色弱群体不可辨且无法覆盖多状态流转；缺乏审核通过的正向微动效与多档高 DPI 平滑适配。
3. **交付物脱节与手工返工**：初始审计记录了封面、事由列、大写金额与命名方面的缺口。汇总最终采用 Decimal 静态值，不采用动态 `=SUM()` 公式。
4. **GUI 架构技术债累积**：本段的 14 个补丁文件及启动时间数据是初始审计快照，不是当前冻结清单或性能验收结果；当前 A-01 冻结 7 个历史 GUI 模块，实际状态见执行计划。

本路线图立足于**“资深桌面端 UI/UX 设计专家”、“打工人一线报销专家”与“桌面软件架构师”**的三重视角，将合规风控基建（B-01 至 B-07）与交互/视觉创新（E-01 至 E-10）全面熔铸为统一的 v0.2.0 规格标准与 3 个 Sprint 落地计划（P0 数据与事由、P1 审核与体验、P2 打磨与治理），为 Invoice Hub 迈向企业级轻量化报销整理利器奠定坚实的工程基石。

## 第 1 节：R1 打工人报销端到端体验与痛点走查 (Employee Reimbursement Experience & High-Friction Path)

### 1.1 报销人员全流程动线走查 (The 5-Stage Journey Walkthrough)

打工人整理报销多发生于每月报销截止日深夜（如 24 日 23:00）。该场景下，用户注意力带宽受限、情绪急躁，对界面的“摩擦力”（如重复点击、阻断报错、缺少保存、需要额外打开 Excel 修改）极度敏感。以下梳理当前系统 5 大阶段的端到端动线及断点：

```
[阶段 1: 多渠道收集] ──> [阶段 2: 解析与补齐] ──> [阶段 3: 事由归组] ──> [阶段 4: 审核核验] ──> [阶段 5: 导出交付]
  · 缺少拖拽支持          · OFD/图片退回           · 事由无处填写         · 420px 挤压大图        · 缺少 A4 封面
  · AP 隔离扫码超时       · 弹窗仅能改 6 字段       · 仅输入单组名称       · 缺少 Space/JK 键      · 缺少第 21 列事由
  · 微信文件沙盒受限      · 缺税号/税额/事由        · 无法继承归类         · 机械连击眼疲劳        · 硬阻断与文件名死板
```

#### 阶段 1：多渠道票据收集 (Multi-Channel Intake)
- **本地导入 (Local Folder)**：当前入口位于 `scripts/invoice_fetch/gui/app.py:9270-9274`，仅通过 `QFileDialog.getExistingDirectory` 弹窗选择文件夹。主窗口全域未实现 `setAcceptDrops(True)`，用户无法从桌面或文件管理器将散落的发票 PDF/图片直接拖拽入软件，迫使用户必须先在 Windows 资源管理器中新建临时文件夹进行搬运。
- **移动端局域网传输 (Mobile LAN Upload)**：由 `scripts/invoice_fetch/gui/mobile_upload_dialog.py` 与 `scripts/invoice_fetch/mobile_upload.py` 驱动。手机在企业办公 Wi-Fi 或酒店 Wi-Fi 下扫描二维码后，因局域网交换机启用了 **AP 隔离 (Client Isolation)**，数据包在数据链路层被直接丢弃，手机浏览器无限转圈超时。用户由于缺乏技术背景，陷入“连了同一 Wi-Fi 为何打不开”的挫败感中。
- **微信发票导入 (WeChat Intake)**：微信发票多存在于微信卡包或聊天记录中。当前移动端 Web 页面 `scripts/invoice_fetch/mobile_upload.py:1431-1434` 仅弹出一行小字：“微信内 PDF 选择受限，建议在浏览器打开”，打工人被迫多步跳转，体验断裂。
- **邮箱自动拉取 (Email Fetching)**：支持 IMAP/POP3 协议批量拉取邮件附件，运行稳定，但若拉取的邮件正文中夹带行程单或说明，与发票之间的关联信息易丢失。

#### 阶段 2：解析与手工补齐 (Parsing & Exception Completion)
- **非标票据被动退回**：在 `scripts/invoice_fetch/services.py:2258-2276` 中，OFD 电子发票被硬编码跳过（`"本地导入暂不支持OFD解析，请人工处理"`），压缩包内的图片票据直接标为待识别，导致大量高铁客票、通用定额发票、打车小票被丢入“异常处理”队列。
- **补齐弹窗字段严重阉割**：当发票解析不全时，双击弹出的编辑窗 `EditFieldsDialog`（位于 `scripts/invoice_fetch/gui/invoice_detail_panel.py:4832-4860`）仅暴露 6 个文本框：发票号码、开票日期、总金额、费用类型、购买方名称、销售方名称。至关重要的财务与事由字段（购买方税号及类型、不含税金额、税额、税率、发票代码、自定义事由说明）全部缺失，用户即便想人工补齐也无法录入，导致数据残缺进入下一阶段。

#### 阶段 3：事由归组与报销单创建 (Claim Grouping)
- **事由在数据层彻底缺失**：数据库设计 `scripts/invoice_fetch/migrations.py:283-291` 中，`claim_groups` 仅有 `id`, `name`, `period_start`, `period_end`, `status`, `created_at`。发票表 `invoices` 亦无事由字段。
- **创建交互原始简陋**：在 `scripts/invoice_fetch/gui/app.py:8373-8379` 中，创建报销组仅通过一行代码 `QInputDialog.getText(self, "新建报销组", "报销组名称（例如：九月项目出差）")`。报销人姓名、所属部门、费用类别（差旅/招待/采购）、详细业务背景均无处安放，全靠用户在组名字符串中“夹带私货”。

#### 阶段 4：单据核验与审核流转 (Batch Verification & Review)
- **发票大图预览严重受挤**：在 `scripts/invoice_fetch/gui/ui/pages/invoice_workbench.py:28, 96-97` 中，右侧审核面板被固定为 420px（`setMinimumWidth(420)` / `setMaximumWidth(420)`），显式注释注明 `# NO Splitter`。在主流 14 英寸 1080p 笔记本（125% 缩放）上，中央工作区的票据扫描件大图被挤压得字迹模糊，打工人不得不左右拖拽滑动条核对开票明细。
- **单键键盘人机工程学缺失**：审核快捷键注册在 `scripts/invoice_fetch/gui/app.py:2721-2726`，仅映射了 `Return/Enter` 为审核通过、`Delete` 为已忽略、`Ctrl+E` 为异常。打工人面对 60-100 张票据时，无法使用现代效率软件通用的 `Space`（快速通过并下一张）、`J`/`K`（下/上行跳格导航），必须高频在鼠标点击与键盘大键之间来回切换。
- **证明材料多对一绑定死锁**：在 `scripts/invoice_fetch/db.py:1978-1984` 与 `2032-2038` 中，绑定证明材料强校验 `mail_uid` 必须完全相等，且一旦绑定，证明材料被立刻执行软删除（`UPDATE invoices SET is_deleted = 1`）。这直接导致打工人一张 ¥800 的往返差旅行程单无法同时关联该趟出差的 4 张打车发票与 1 张住宿发票（1:N 共享证明材料），被迫人为拆解或财务退单。

#### 阶段 5：导出打包与财务对接 (Export & Submission)
- **台账明细缺少事由列**：`scripts/invoice_fetch/excel_export.py:19-40` 定义的 20 列中无“报销事由”，打工人在导出后必须重新用 Excel 打开文件，逐行手动粘贴填报事由，极度耗时且容易串行。
- **导出文件名死板固定**：`scripts/invoice_fetch/claim_export.py:532` 中导出文件被固定硬编码为 `reimbursement.xlsx`，必须手工改名为符合公司财务规范的名称（如 `202610_销售部_张三_出差报销.xlsx`）。
- **校验阻断逻辑矛盾冲突**：在 `scripts/invoice_fetch/claim_export.py:399-406` 中，缺补充材料时抛出 `ValueError("导出已阻断：缺补充材料...")` 强行崩溃阻止导出，但前置审核流 `scripts/invoice_fetch/gui/app.py:8258-8270`（`_set_selected_status` 仅校验 `is_pending_evidence_invoice`，放行 `missing_extra` 为已通过）却允许用户在缺少材料时轻量放行为“已通过”，造成前后台行为不一致，让赶在截点提交的用户遭遇“导出阻断假死”。

#### 2. 无票号弱匹配与人工复核 (Weak Match Review)
- 非空票号（包括短票号）不进入弱匹配流程；只对无票号记录比较销售方、有效日期、Decimal 金额和币种。
- 缺失或无效数据不匹配，不把未知币种当作人民币；相同匹配键也不等于发票相同。
- 复核标记与审核状态分离。用户可查看两张原件、确认不同、确认重复或重置结论；这些操作不删除票据，也不改写审核状态。
- 尚未确认的弱匹配不阻断导出；人工确认重复的记录按导出安全规则处理。详情见开发执行计划。

当前对话框显示候选记录编号、销售方、费用日期和金额，并允许分别打开两张原件。用户可确认不同、确认重复或重置结论。确认重复只记录复核结果，不会自动删除或忽略票据；确认重复的票据会阻断报销组导出，需回审核页忽略或重置。

#### 3. 手机上传 AP 隔离诊断
- 诊断由电脑端可达入口提供，指出同一网络、AP 隔离、切换手机热点和桌面拖拽等排查步骤。
- 不要求手机页面在无法连接电脑时自行显示诊断卡片，也不承诺网卡自动切换或旧二维码自动重绘。
- 真实手机和局域网验收仍是发布前置项。

#### 4. 键盘操作与批量审核（当前实现）

- 审核页 `Up` / `Down` 移动当前选择；`Return` / `Enter` 标记通过，`Delete` 忽略，`Ctrl+E` 标记异常，`Ctrl+G` 将当前行加入详情区选中的报销组。
- `Ctrl+B` 折叠/恢复审核详情面板。`Space`、`A`、`J`、`K`、`X` 和单独的 `E` 不属于当前审核快捷键契约。
- 批量操作区位于列表下方，不使用原提案中的悬浮动画条。批量审核会预检资格、展示跳过原因，并在执行前重新核对记录是否变化；疑似重复、财税异常、缺少原件或证明材料等记录不会被批量通过。批量添加报销组仍通过原有批量按钮操作。

#### 5. 1:N 证明材料多对一关联体系 (invoice_evidence_relations)
- **解耦 `mail_uid` 限制**：废除仅同邮件才可关联的刚性代码。
- **构建关系表结构**：
  ```sql
  CREATE TABLE IF NOT EXISTS invoice_evidence_relations (
      invoice_id INTEGER NOT NULL,
      evidence_id INTEGER NOT NULL,
      created_at TEXT NOT NULL DEFAULT (datetime('now', 'localtime')),
      PRIMARY KEY (invoice_id, evidence_id),
      FOREIGN KEY (invoice_id) REFERENCES invoices(id) ON DELETE CASCADE,
      FOREIGN KEY (evidence_id) REFERENCES invoices(id) ON DELETE CASCADE
  );
  ```
- **共享生命周期**：关联证明材料时，严禁软删除 `evidence_id` 发票记录，保持其公开可用性，允许多张打车票或餐饮票同时引用同一张出差派遣单或行程汇总单。

## 第 3 节：R3 报销单交付标准与 Excel 导出规格设计 (Reimbursement Ledger & Cover Sheet Architecture)

### 3.1 报销单 Excel 封面与打印设置

报销组导出会把【费用报销单】插入工作簿首位；原主明细工作表仍叫【发票汇总】，并保留【分类汇总】和【异常待处理】工作表。封面实现位于 `scripts/invoice_fetch/claim_cover.py`，是纵向 A4、单页适配，内容包括报销组、报销人、部门、事由分类与说明、票据数量、报销金额、金额大写、签字/复核、报销期间和生成日期。

封面使用 A:F 六列，以 A1:F1 合并标题；其余字段按纵向标签和值布局。实际行号和打印效果以代码为准。表格不含原提案中的报销单编号、税额合计和多栏矩阵。A4 设置已写入工作簿；Excel/WPS 显示与实体打印预览仍是发布前验收项。

### 3.2 汇总值与工作簿完整性

当前实现使用 Decimal 计算封面、明细和汇总中的金额，并写入静态数值。`openpyxl` 不能通过普通公式赋值可靠地同时写入公式缓存值，因此不生成 `=SUM()` / `=COUNTA()` 公式。若在办公软件中删除或调整明细行，应重新从应用导出，以刷新总额和张数。

Manifest 对实际导出的文件记录 SHA-256 和文件大小，可发现文件缺失或清单未同步更新时的文件变化。该机制不是数字签名；若清单与文件一起被替换，不能据此证明来源或防止蓄意篡改。

### 3.3 中文大写金额转换

封面金额大写由 `scripts/invoice_fetch/claim_cover.py:rmb_upper` 生成：输入经 `Decimal` 解析，按分位四舍五入，拒绝非有限值和超出支持范围的金额，并处理负数。实现本身不是人民银行认证，也不应把初始提案中的伪代码或基准清单当成现行代码契约。相关边界由 `tests/test_claim_cover.py` 覆盖；显示及财务格式仍需在目标办公软件中验收。

### 3.4 明细台账报销事由与继承规则

#### 1. 工作表与字段顺序

基础导出明细表为【发票汇总】；报销组导出会把【费用报销单】封面插入首位，不会把基础明细表重命名为【发票明细】。当前 `scripts/invoice_fetch/excel_export.py` 的 `_COLUMNS` 字段顺序如下：

#### 2. 事由解析

`reimbursement_reason` 是明细第 21 列。`custom_reason` 为 NULL 时继承报销组的事由分类和说明；显式空字符串表示清空事由；非空覆盖值优先。组默认值不会复制进单票字段。解析逻辑位于 `scripts/invoice_fetch/claim_reason.py`。报销组导出会将解析后的实际事由写入明细与 Manifest。

金额与票数以应用导出时的记录计算并写为静态值，不使用 Excel 公式。用户在导出后修改明细时，应重新从应用导出以更新汇总。

### 3.5 导出文件名模板与文件名清理

`scripts/invoice_fetch/claim_cover.py:claim_filename` 当前支持 `{YYYYMM}`、`{部门}`、`{姓名}`、`{事由}` 四种占位符；未知或不完整占位符会报错。事由优先取详细说明、分类，再回退报销组名称；部门和姓名缺失时分别回退为“未填部门”“未填姓名”。模板留空时使用 `reimbursement.xlsx`。

生成文件名时会替换 Windows 禁止字符、去除尾随点/空格、处理设备保留名，并将文件主体限制在 110 个字符内。该限制针对文件名本身，不保证任意深层目录都不会触及 Windows 路径限制；长路径与目标办公环境仍需实际验证。当前不支持 `{YYYY}`、`{YYYYMMDD}`、`{金额合计}` 或 `{张数}`。

#### 事件中介契约规范 (Signal-Slot Mediation Contract):
- **View 层**：仅继承 `QWidget`，负责 UI 布局与控件事件捕获，通过 `Signal` 向外抛出用户意图（例如 `claimCreateRequested = Signal(dict)`）；
- **Controller 层**：继承 `QObject`，负责持有业务逻辑，订阅 View 的 `Signal`，调用 `services.py` 或 `db.py` 执行真实落库，最后通过 Slot 更新 View 的呈现状态；
- **禁止交叉越权**：View 层严禁直接引入 `sqlite3` 连接、严禁直接执行 `openpyxl` 导出；Controller 层严禁包含任何直接的像素绘制逻辑。

### 4.4 冷启动性能治理与 openpyxl 泄漏根治（历史诊断记录）

#### 1. 历史冷启动测量
以下数字来自历史开发环境测量，不是最终 Windows 安装包的发布证据：
- Baseline 冷启动安全预算：$\le 5000\text{ ms}$；
- 优化前当前实测冷启动首帧绘制（First Paint）：**~1,904 ms**（符合基线要求，但存在偶发劣化隐患）。

#### 2. 意外引入的 heavy import 泄漏根因定位
在 `scripts/invoice_fetch/gui/business_pages_baseline.py:13` 中存在如下代码：
```python
from ..claim_export import _normalize_export_date_prefix
```
- **依赖传播链穿透**：
  `business_pages_baseline.py` $\longrightarrow$ `claim_export.py` $\longrightarrow$ `excel_export.py` $\longrightarrow$ **`import openpyxl`**。
- **开销度量**：openpyxl 作为庞大的第三方法规解析器，仅静态模块导入耗时即达到 **421.30 ms**（占整体冷启动耗时的 22.1%）。
- **泄漏事实**：用户在仅仅启动桌面端、甚至尚未进入导出页面前，`openpyxl` 已经被提前强制载入内存。

#### 3. 根治方案与压降效果
- **解耦动作与执行时序**：将解耦动作明确设定为 **Sprint P0 的即时前置必选任务**，以避免导出依赖泄漏至 GUI 启动路径。将 `_normalize_export_date_prefix` 纯字符串辅助函数在 `business_pages_baseline.py` 中就地私有实现，彻底切断对 `claim_export.py` 的顶层导入依赖；
- **冷启动压降收益**：
  $$\text{Startup Time} = 1,904\text{ ms} - 421\text{ ms} \approx \mathbf{1,483\text{ ms}}$$
  实测不仅能彻底根除 `openpyxl` 静态加载惩罚，还可将 `business_pages_baseline.py` 自身导入时间从 907.66 ms 骤降至 198.45 ms（净降 709.21 ms / 降幅 78.1%），冷启动响应速度提升 22% 以上，全流程首帧绘制达标 $\le 1,480\text{ ms}$。

#### 4. 核心重量级库按需延迟载入健康度检验 (Lazy Loading Status)
- `pdfplumber`：在 `invoice_parser.py:152-155` 中已被严格放置于发票解析方法内部局部导入，冷启动期间耗时为 0 ms；
- `PySide6.QtPdf`：在 `pdf_preview_controller.py:58` 中已被放置于预览请求触发时局部导入，冷启动期间耗时为 0 ms。

#### 1. 合规风控基建全集 (Compliance Baselines B-01 ~ B-07)
- **B-01: 购买方税号和证件类型**：持久化税号类型；保留未知/未采集状态，按类型校验，不对所有票据强制 18 位；

- **B-06: 财税字段编辑**：审核详情可编辑税号及类型、税前金额、税额、税率和发票代码；报销事由按独立编辑路径处理；
