# Invoice Hub v0.1.6 Interaction Freeze

Status: **interaction-design authority for the v0.1.6 maintenance candidate**.

This document is an addendum to `docs/DESIGN_BASELINE_V1.md`. It does not
rewrite the historical baseline. Where the v1.0 baseline and this addendum
conflict for the surfaces named below, this addendum is authoritative for
v0.1.6 and later maintenance work until a newer approved design document
supersedes it.

## 1. Product character

Invoice Hub remains a restrained, local-first personal reimbursement utility.
The interface should optimize for fast collection, confirmation, review and
export rather than presenting technical telemetry as product content.

Principles:

- one visible owner for each piece of information;
- user-facing state before implementation detail;
- progressive disclosure for diagnostics;
- explicit consent before any Windows Firewall mutation;
- local confirmation before upload when a source is ambiguous;
- automated geometry checks do not replace human visual review.

## 2. Page archetypes

The existing page archetypes remain in force:

- **Standard** — centered, bounded informational/configuration pages;
- **Workspace** — dense review surfaces that use available width;
- **Task Flow** — source/task/result pages with a bounded desktop host.

Dashboard, Review Workspace and reimbursement/export interaction are frozen by
this addendum. They may receive defect fixes, but v0.1.6 mobile work must not
redesign them.

## 3. Settings compact amendment

The Settings Golden Page remains authoritative at normal desktop widths.
At constrained logical widths, including Windows 125%/150% scaling, the
following responsive behavior is explicitly allowed:

- account/profile list and detail surface may stack;
- action footers may reflow when a one-line footer would clip or overlap;
- long explanatory values wrap and grow vertically;
- paths use middle elision plus a full-value tooltip;
- controls must not shrink text below the design baseline merely to fit.

No important text may be silently clipped or covered by an action.

## 4. Import Center — normal sources

For mailbox and local-file tasks, the existing Task Flow remains:

`source selector | task | recent/result summary`

The source and result columns may use bounded responsibility widths while the
task region expands.

## 5. Import Center — mobile-active source

Mobile Upload is a complex task and is not constrained to the same narrow task
column as mailbox/local import.

When Mobile Upload is starting or active, **the parent Import Workspace owns
responsive width allocation**. The child panel must not infer the desktop page
layout from an already-squeezed child size hint.

Desktop contract:

- at normal desktop widths, the active mobile task receives enough width for a
  QR/status two-column layout; target task allocation is approximately
  760–900 logical px, with at least 720 logical px available to the embedded
  panel where the outer workspace permits it;
- the source selector and recent-run summary remain available, but may become
  narrower than their normal-source widths;
- if the outer workspace genuinely cannot provide the mobile minimum, the
  **outer workspace stacks first**; only a genuinely narrow embedded surface
  may use the panel's vertical fallback;
- an internal narrow debug scroll column is prohibited.

## 6. Desktop Mobile Upload

The active desktop surface is a user task, not a diagnostics dashboard.

### Default information

Show:

- QR code;
- copy-link action;
- selected network;
- local self-check as `正常 / 失败 / 检查中`;
- Windows Firewall user-facing state;
- LAN-client reachability as `尚未确认 / 已确认`;
- latest confirmed LAN access time;
- current upload result counts;
- network switch and stop actions.

### Technical details

Raw implementation data belongs under a collapsed **技术详情** disclosure:

- bind address;
- public address/port;
- interface priority;
- virtual-interface flag;
- raw self-check state;
- raw firewall state.

Do not repeat the same address in multiple default rows.

### Layout

Normal desktop:

`QR / link | connection status`

Footer actions remain content-width and horizontal where space permits.
Do not create a tall 200–250 px-wide internal details strip merely to preserve
three outer columns.

`UI-MOBILE-DESKTOP-001` is frozen once native screenshots confirm this contract
at the accepted desktop/DPI matrix.

## 7. Firewall state model

These states are deliberately independent:

1. **Service running** — the HTTP listener exists.
2. **Local self-check** — the PC can open its selected LAN URL.
3. **Windows Firewall authorization** — a rule matching the approved contract
   is observable.
4. **LAN access confirmed** — a valid external LAN client actually reached
   `/u/<token>` with HTTP 200.

Never infer state 4 from states 1–3.

### Packaged build

Formal `InvoiceHub.exe` authorization requires explicit user confirmation and
UAC. The accepted persistent rule is:

- current `InvoiceHub.exe` only;
- inbound;
- allow;
- TCP;
- Private profile only;
- program-scoped; the current random listener port is not exposed as a global
  `Program=Any` rule.

Public-network authorization is not part of this product flow.

### Source/development build

`python.exe`, `pythonw.exe` and `pytest.exe` must never receive a persistent
Any-Port rule.

A developer may explicitly request a test rule scoped to:

- current development executable;
- Private profile only;
- TCP;
- the current Mobile Upload port only.

**Starting, stopping or shutting down Mobile Upload must not mutate Windows
Firewall or unexpectedly trigger UAC.**

Existing Invoice Hub development-marker rules are detected read-only. Cleanup
is a separate, explicit user action. A stale random-port rule is not equivalent
to authorization for the current session.

## 8. Mobile Web Upload

The mobile interaction is frozen as:

`choose source -> review selected content -> explicit upload`

### Source selection

Use compact, touch-friendly actions for:

- file/PDF/OFD;
- gallery image;
- camera.

Touch targets are at least 44 logical CSS px. Selection does not upload.

### Review cards

Before POST:

- images show a local thumbnail and can open full-screen preview;
- PDF uses vendored, local PDF.js to obtain page count and a real first-page
  thumbnail;
- PDF can open a full-screen, lazy-rendered multipage review surface;
- OFD clearly states that mobile content preview is unavailable;
- broken/unpreviewable PDF blocks silent upload and offers remove/reselect;
- long filenames preserve the extension, use at most two visible lines, and
  retain the full accessible/title value.

PDF/image preview is local to the phone browser until the user presses Upload.
No CDN or third-party preview service is allowed.

### PDF zoom

The PDF review surface defaults to fit-to-width but **must not disable browser
or pinch zoom**. Users must be able to enlarge invoice number, tax ID, date,
amount and line-item content before uploading.

Do not ship `user-scalable=no` or an equivalent accessibility/zoom lock.

### Upload action

The upload action is a sticky safe-area-aware CTA showing selected count/size.
It must not obscure the final review card. Upload result feedback is inline;
browser `alert()` is not used.

### Session metadata

The primary mobile page uses user language. It may show the destination host
and an approximate expiry message. Internal batch identifiers belong to
logs/diagnostics rather than the default page.

## 9. WeChat behavior

When the page is opened inside WeChat:

- image/gallery/camera use remains available where the WebView permits it;
- PDF/file-picker limitations are explained in a compact expandable hint;
- the user is instructed to use the external/system browser for the full PDF
  review flow when necessary;
- the page must not claim that the handoff succeeded without real-device
  evidence.

## 10. Responsive ownership

Breakpoints are owned by the highest layout level that understands the task:

- App/Import Workspace decides when the Task Flow rearranges;
- MobileUploadSessionPanel only switches its internal QR/status arrangement
  when its assigned surface is genuinely narrow;
- the mobile web page owns its CSS viewport behavior.

A child size hint must not create a feedback loop that forces the parent into a
narrow layout on an otherwise wide desktop.

## 11. Acceptance authority

Evidence classes are not interchangeable:

- synthetic/offscreen geometry **does not equal** human visual acceptance;
- Chromium browser smoke **does not equal** Android or WeChat acceptance;
- local self-check **does not equal** phone/LAN reachability;
- firewall-rule presence **does not equal** LAN reachability;
- source tests **do not equal** packaged Windows acceptance.

Before `MOBILE-NET-001` closes, a source-matched packaged `InvoiceHub.exe` must
complete: missing-rule state -> explicit authorization/UAC -> valid Private
rule -> real-phone GET 200 -> real upload/import.

Before `UI-UPLOAD-001` closes, Android real-device testing must cover PDF first
page, multipage navigation, zoom, image preview, long filename, sticky CTA and
actual upload. WeChat acceptance additionally covers the external-browser
handoff.

## 12. Freeze boundary

Once the remaining items in this addendum are implemented and the source gates
are green:

- `V0.1.6 INTERACTION DESIGN = FROZEN`;
- Dashboard / Review / Export / Desktop Mobile Upload receive bug fixes only;
- PR #107 remains Draft until packaged Windows and Android/WeChat acceptance
  complete;
- v0.1.5 / v0.1.5-rc7 tags, Releases and assets remain immutable.
