## 1. 执行摘要 (Executive Summary)

### 1.1 总体代码健康度评价与发布就绪性裁决
在 v0.1.8 准备阶段，开发团队针对第一轮代码审查报告（`CODE_REVIEW_REPORT.md`）中的高危缺陷展开了针对性的集中攻坚。审查团队确认，在 **UI 异步响应性能、线程生命周期控制与安全优雅退出、Excel 公式注入防护、SQLite 事务回滚以及 Workbench 响应式布局测试门禁恢复** 等方面，系统取得了重大且令人信服的工程质量改进。

然而，基于本次对全仓 1,559 个测试用例的真实执行、45 个变更文件的代码级审查、以及前次 41 项缺陷的闭环复核，审查团队给出严格的发布就绪性结论：
**🔴 CONDITIONAL REJECT / 暂不具备直接发布上线条件 (NOT READY FOR RELEASE)**。

系统目前存在 **3 项 Critical 级发布阻断项 (Release Blockers)** 及若干 High 级质量风险，必须在发布正式 Tag 之前彻底清零。

### 1.2 核心质量提升确认
1. **工作线程退出与生命周期安全彻底闭环 (`ISSUE-CRIT-01`)**:
   主窗口 `closeEvent` 统一接管了 `scan_worker`、`import_worker`、`_export_migration_worker`、`_hci_history_worker` 和 `_redownload_worker`。先协同发起取消，断开信号连接并安全 `wait()`，确保所有后台工作线程平稳终止后才关闭 SQLite 数据库；新增 `_worker_callback_allowed` 守卫，彻底消除了窗口关闭后延迟信号触碰已释放 C++ 控件的段错误（`0xC0000005`）崩溃隐患。
2. **核心业务路径全面异步化，告别 UI 假死 (`ISSUE-HIGH-04`, `ISSUE-HIGH-05`)**:
   彻底重构“发票重新下载”与“邮箱连接测试”。发票重新下载抽取为独立的 `redownload.py` 领域服务与 `RedownloadInvoicesWorker(QThread)`；邮箱连接测试封装为 `MailboxConnectionTestWorker(QThread)`，彻底移除了主线程同步 IMAP/HTTP 网络请求与危险的 `QApplication.processEvents()` 重入调用。
3. **安全注入与事务悬挂加固 (`ISSUE-HIGH-01`, `ISSUE-HIGH-02`)**:
   补齐了 Excel 导出“异常待处理”工作表的公式注入转义 `_safe_excel_value`；在 `db.py` 捕获 `IntegrityError` 时显式调用 `self._conn.rollback()`，根除了事务悬挂引发后续写操作锁死的问题。
4. **CI 布局门禁恢复 (`ISSUE-CRIT-03`)**:
   将 `test_workbench_layout.py` 中依赖特定物理桌面分辨率的原生测试剥离至 `tests/test_workbench_native_geometry.py`，使 897 行纯布局断言与响应式计算逻辑重新回归 CI 单元测试门禁。
5. **GUI 架构技术债首期偿还 (`ISSUE-MED-06`)**:
   退役了 5 个临时补丁模块，`check_architecture_policy.py` 白名单从 24 项降至 19 项。

### 1.3 三大 Critical 级发布阻断项 (Release Blockers)
1. **🔴 CI 流水线 master 分支依然缺少 `push` 触发器 (`ISSUE-CRIT-02` / `ISSUE-CRIT-NEW-01`)**:
   `.github/workflows/ci.yml:6-10` 依然仅声明了 `pull_request: branches: [master]`。任何直接推送到 `master` 的 commit（如版本号 bump、发版 commit）或 PR 合并入主干后，GitHub Actions 完全不运行，主干分支处于裸奔脱保状态。
2. **🔴 `is_duplicate` 粗暴按（销售方+金额）判重导致合法发票被静默误丢弃 (`ISSUE-HIGH-03` / `ISSUE-CRIT-NEW-02`)**:
   `db.py:502-508` 与 `services.py:3277-3282` 依然保留该缺陷逻辑。当发票号码缺失（如出租车发票、定额发票）或号码暂未提取时，同一销售方同金额的合法发票（如每月固定 50 元话费、同日多笔固定车费）第二张及后续处理时被直接认定为重复发票而静默抛弃，导致财务真实凭据严重丢失。
3. **🔴 CI Shard 1 因外来电力测试文件零用例而直接报错中断 (`ISSUE-CRIT-NEW-03` / `ISSUE-HIGH-12`)**:
   工作区遗留的外来电力仿真测试 `tests/test_ppc_m3_protocol_verification.py` 被 CI 隔离运行器 `run_isolated_unittest.py` 分配至 Shard 1。由于该文件为纯 pytest 脚本、未继承 `unittest.TestCase`，`unittest` 探测出 0 个测试。运行器判定“报告 0 个执行测试不属于有效发布凭据”，直接退出码 2 终止构建，导致 CI Shard 1 必然全红崩溃。

#### [ISSUE-CRIT-NEW-02] `is_duplicate` 仅凭（销售方+金额）误去重导致合法真实发票静默丢失 (前次 ISSUE-HIGH-03 升格)
- **严重级别**: 🔴 Critical
- **文件路径与行号**:
  - `scripts/invoice_fetch/db.py:502-508`
  - `scripts/invoice_fetch/services.py:3277-3282`
- **根本原因分析**:
  在 `scripts/invoice_fetch/db.py:502-508` 中：
  ```python

          f"SELECT 1 FROM invoices WHERE total_amount = ? AND seller_name = ?{cond}",

  在 `services.py:3277-3282` 中调用：

      set_process_outcome("duplicate")
      return ProcessEmailResult(...)
  ```
  若发票号码缺失（如出租车发票、定额发票、或者 OCR/解析器暂未提取出号码），只要同一销售方开出相同金额发票，第二张及后续发票直接返回 `is_duplicate = True` 并被静默跳过。
- **影响分析**:
  严重的业务数据静默丢失。财务发票系统必须确保真实入账凭证一张不漏，同销方同金额（如每月话费、每日打车）属于极高频真实场景，误判去重属于业务级致命缺陷。
- **整改方案与代码示例**:
  修改 `db.py:is_duplicate`，仅在有发票号码时按 `(invoice_number, total_amount, seller_name)` 去重；若无发票号，必须复合唯一键判定（如 `expense_date`、`file_hash` 或 `mail_uid`），禁止仅凭销方+金额判重：
  ```python
  def is_duplicate(self, invoice_number: str, total_amount: str = "",
                   seller_name: str = "", include_deleted: bool = False,
                   file_hash: str = "", expense_date: str = "") -> bool:
      invoice_number = (invoice_number or "").strip()
      total_amount = (total_amount or "").strip()
      seller_name = (seller_name or "").strip()
      file_hash = (file_hash or "").strip()
      cond = "" if include_deleted else " AND is_deleted = 0"

      if invoice_number and total_amount:
          row = self._conn.execute(
              f"SELECT 1 FROM invoices WHERE invoice_number = ? AND total_amount = ?{cond}",
              (invoice_number, total_amount),
          ).fetchone()
          if row is not None:
              return True

      if file_hash:
          row = self._conn.execute(
              f"SELECT 1 FROM invoices WHERE file_hash = ?{cond}",
              (file_hash,),
          ).fetchone()
          if row is not None:
              return True

      if not invoice_number and seller_name and total_amount and expense_date:
          row = self._conn.execute(
              f"SELECT 1 FROM invoices WHERE seller_name = ? AND total_amount = ? AND expense_date = ?{cond}",
              (seller_name, total_amount, expense_date),
          ).fetchone()
          return row is not None

      return False
  ```

### 3.3 🟡 Medium 级别新缺陷 (中危缺陷 — 架构设计与性能隐患)

1. **[ISSUE-MED-NEW-01] `list_review_invoices` 动态生成巨型 CASE/WHEN 排序语句参数爆炸**
   - **位置**: `scripts/invoice_fetch/db.py:1320-1323`
   - **分析**: 当 `query.invoice_ids` 包含成百上千个 ID 时，SQL 拼接 `ORDER BY CASE i.id WHEN ? THEN 0 WHEN ? THEN 1 ...`，参数量达 `2 * len(ids) + 2`。SQL 膨胀至数万字节，导致 SQLite 失去 B-Tree 索引排序能力，严重消耗 CPU。

## 4. 架构与异步健康度综合评估 (Architecture & Async Health Assessment)

### 4.1 多线程工作者体系架构 (`workers.py`)
在 v0.1.8 中，项目将耗时的 I/O 和网络操作全面迁移至 `QThread` 体系，形成了四类标准工作线程：
1. `RedownloadInvoicesWorker(QThread)`：处理多发票重新拉取、OFD 还原、链接下载与 PDF 解析；
2. `MailboxConnectionTestWorker(QThread)`：处理设置界面的 IMAP 连接连通性握手与验证；
3. `LocalImportWorker(QThread)`：处理本地目录及 ZIP 压缩包递归解压入库；
4. `EmailScanWorker(QThread)`：处理主界面的远程邮件扫描与抓取。

各 Worker 均采用“请求对象（Request Dataclass）入参 + 信号（Signal）出参”的松耦合设计，严格杜绝了子线程直接访问主窗口 UI 控件的危险模式。

### 4.2 线程生命周期与安全退出机制评估
主窗口 `closeEvent` 的退出逻辑是本次重构的最大亮点：
```python
# scripts/invoice_fetch/gui/app.py:848-877 (_shutdown_background_workers)
def _shutdown_background_workers(self) -> None:
    self._shutdown_requested = True
    for attr, label, worker in list(self._active_background_workers()):
        if getattr(worker, "isRunning", lambda: False)():
            self._disconnect_worker_signals(worker)
            worker.blockSignals(True)
            if hasattr(worker, "request_cancel"):
                worker.request_cancel()
            worker.wait()
```
- **生命周期保护**: 统合 5 大 Worker，退出时切断信号、请求取消并同步 `wait()`，确保线程执行结束；
- **防悬挂与防崩溃**: 引入 `_worker_callback_allowed()`，即使 Qt 事件队列中残存未投递的 Worker 回调信号，由于 `_shutdown_requested = True`，回调函数直接短路返回，彻底避免已死 C++ 表格被操作；
- **数据安全**: 严格将 `self.db.close()` 放置在所有线程确认停止之后执行，防止后台线程写入时数据库连接被中途销毁引发 SQLite 锁损坏。

### 4.3 协同取消机制 (`ScanControl`)
`ScanControl` 提供了轻量级原子取消标记。在 `redownload.py` 和 `local_import` 中，工作线程在每处理一张发票或一个文件之间均调用 `ctrl.check_cancelled()`：
- 避免了强行 `terminate()` 导致的内存泄漏与句柄锁死；
- 保障了已完成项目的原子入库，未处理项目的干净丢弃；
- `test_local_import_cancellation.py` 8 个测试用例充分验证了该机制的边界有效性。

### 4.4 响应性与猴子补丁退役现状
- **主线程响应性**: 移除了旧版中直接在 GUI 线程执行 IMAP 连接与 `processEvents()` 重入的危险代码，界面假死现象被根除。
- **Patch 模块退役现状**: 虽然退役了 5 个文件名带 `_fix` 的补丁模块，使架构守卫 `check_architecture_policy.py` 通过，但 `review_baseline_pipeline.py` 的 11 阶段和 `settings_baseline_pipeline.py` 的 9 阶段后置补丁逻辑未变。未来仍需推进组件自包含构造。
