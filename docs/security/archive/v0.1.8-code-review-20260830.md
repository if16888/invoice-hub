## 2. 执行摘要 (Executive Summary)

Invoice Hub 具备高度专业和成熟的防御性工程底座：网络层实现了严密的公网 IP 校验与抗 SSRF/DNS-Rebinding 机制；文件处理层实现了防 Zip Slip 路径穿越、解压炸弹限制及魔数（Magic Bytes）校验；CI 构建了敏感词扫描、导出合规、版本元数据及冷启动性能（≤2000ms）的多维自动化门禁；测试套件包含 1,400+ 测试用例与双 Oracle HCI 验收体系。

然而，在最新一轮大规模重构后，系统在**线程生命周期管理、主线程阻塞性 I/O、CI 门禁触发策略、重构命名空间一致性以及部分安全边界**上暴露了多项严重与高危缺陷：
1. **Critical 级缺陷**：
   - `gui/app.py` 的 `closeEvent` 完全遗漏了对后台 `import_worker` 和 `_hci_history_worker` 的等待与清理，在窗口关闭时立即销毁数据库连接，极易引发 SQLite 写入中断损坏与已销毁 C++ Qt 对象的严重崩溃；
   - `.github/workflows/ci.yml` 缺少 `push: branches: [master]` 触发器，导致合并至 master 的代码完全脱离 CI 保护；
   - `tests.test_workbench_layout`（共 1,322 行响应式布局断言）因单个原生 GUI 测试而被 CI runner 默认排除并在 `ci.yml` 中被显式跳过。
2. **High 级缺陷**：
   - `excel_export.py` 导出“异常待处理”工作表时遗漏公式注入（Formula Injection）转义；
   - `db.py` 捕获 `IntegrityError` 时缺少 `rollback()`，存在隐式事务悬挂风险；
   - `is_duplicate` 仅凭（销售方+金额）判定重复，导致同金额高频合法发票被误判拦截；
   - GUI 主线程直接执行同步 IMAP 网络连接与 HTTP 下载导致界面冻结（假死）；
   - `__main__.py` 跨模块直接篡改 `services.py` 私有全局变量 `_rename_source_mode`；
   - AI 设置界面存在伪造成功结果的桩方法；
   - `preview_mixin.py` 存在整段 32 行一字不差的重复代码块；
   - 测试用例 Mock 目标大量滞留在 `__main__.py` 而未更新至 `services.py`；
   - 根目录残留电力仿真外来测试文件。
3. **Medium/Low 级缺陷**：
   - `services.py` 膨胀为 4,127 行“上帝模块”；GUI 直接穿透调用 `db._conn.execute`；SQLite 未启用外键约束导致悬空记录；批量 `IN` 查询缺少分块保护。

**综合代码健康度评定**：**B (良好但存在关键并发与重构尾随缺陷，必须在发布前完成 P0/P1 修复)**。

### 3.2 🔴 Critical 级别问题（严重缺陷 — 必须立即修复）

#### [ISSUE-CRIT-01] `closeEvent` 遗漏 Worker 生命周期管理，窗口关闭引发 SQLite 损坏与 Qt 内存崩溃
- **严重级别**: 🔴 Critical
- **文件路径**: `scripts/invoice_fetch/gui/app.py`
- **行号范围**: L927 - L1025
- **所属类别**: Qt GUI / 线程安全 / 数据一致性
- **技术分析 & 影响**:
  在 `InvoiceReviewApp.closeEvent` 中，窗口关闭流程显式检查并等待了 `mobile_upload_controller`（L935-L955）、`_export_migration_worker`（L957-L977）和 `scan_worker`（L978-L999），但**完全没有检查或等待正在运行的 `self.import_worker`（`LocalImportWorker`）和 `self._hci_history_worker`（`HistoryRecheckWorker`）**。紧接着在 L1017 无条件调用了 `self.db.close()`。
  若用户在本地文件夹导入（可能包含数百张 PDF）或历史记录重检过程中关闭主窗口：
  1. 后台 `LocalImportWorker` 依然在工作线程中调用 `import_local_directory` 并向 SQLite 数据库执行批量写入；
  2. 主线程已执行 `self.db.close()` 并将 `self.db._conn = None`；
  3. 后台线程写入崩溃或由于主线程连接销毁导致正在提交的事务中断，触发 SQLite 数据库锁损坏；
  4. Worker 执行完毕后触发主线程槽函数 `_import_local_finished` -> `self._load_invoices`，访问已销毁的 C++ Qt 表格控件，直接引发 `0xC0000005` 内存段错误。
- **推荐修复方案**:
  在 `closeEvent` 中统合所有已登记后台 Worker，实施统一的协同取消与阻塞等待：
  ```python
  # 推荐修复代码 (scripts/invoice_fetch/gui/app.py: closeEvent)
  active_workers = [
      ("_export_migration_worker", "旧导出目录迁移", None),
      ("scan_worker", "邮箱扫描", lambda w: getattr(w, "request_cancel", lambda: None)()),
      ("import_worker", "本地导入", None),
      ("_hci_history_worker", "历史记录重检", None),
  ]
  for attr, op_name, cancel_cb in active_workers:
      worker = getattr(self, attr, None)
      if worker is not None and getattr(worker, "isRunning", lambda: False)():
          self.statusBar().showMessage(f"正在等待{op_name}任务安全结束，请稍候…")
          if cancel_cb:
              cancel_cb(worker)
          worker.wait()
          self._end_data_operation(op_name)
  ```

#### [ISSUE-CRIT-02] CI 流水线缺少 `push: branches: [master]` 触发器，主干合并失去门禁防护
- **严重级别**: 🔴 Critical
- **文件路径**: `.github/workflows/ci.yml`
- **行号范围**: L6 - L10
- **所属类别**: CI/CD / 质量基础设施
- **技术分析 & 影响**:
  `.github/workflows/ci.yml` 中的触发条件仅配置了：
  ```yaml
  on:
    pull_request:
      branches:
        - master
  ```
  该配置仅在针对 `master` 创建或更新 PR 时触发。当 PR 被合并（Merge/Squash/Rebase）入 `master`，或者有直接推送到 `master` 的 commit 时，GitHub Actions 不会触发任何构建与测试。
  若合并冲突解决失误、依赖锁文件更新不一致或未走 PR 流程提交热补丁，主干代码将处于无测试验证状态，潜在缺陷将直接流入发布构建阶段。
- **推荐修复方案**:
  在 `on:` 中明确补充 `push: branches: [master]`：
  ```yaml
  on:
    pull_request:
      branches:
        - master
    push:
      branches:
        - master
  ```

- **严重级别**: 🟠 High
- **文件路径**: `scripts/invoice_fetch/excel_export.py`

#### [ISSUE-HIGH-02] 数据库操作捕获 `IntegrityError`/异常后缺少 `rollback()`，导致事务状态悬挂
- **严重级别**: 🟠 High
- **文件路径**: `scripts/invoice_fetch/db.py`
- **行号范围**: L175-L184 (`upsert_email`), L514-L522 (`insert_invoice`), L783-L793, L828-L858, L1001-L1010, L1338-L1348
- **所属类别**: 数据库 / 事务安全
- **技术分析 & 影响**:
  Python `sqlite3` 连接在执行 DML 语句（`INSERT`/`UPDATE`/`DELETE`）时会自动开启隐式事务。当 `execute()` 抛出 `sqlite3.IntegrityError` 或其他异常时，该事务并未自动关闭。如果直接 `return False` 或跳过而不执行 `self._conn.rollback()`，连接上的后续写操作将与上一条失败语句处于同一未回滚的脏事务中，引发锁悬挂或后续批量操作逻辑混乱。
- **推荐修复方案**:
  统一使用 `with self._conn:` 上下文管理器或显式 `rollback()`：
  ```python
  try:
      with self._conn:
          self._conn.execute(...)
      return True
  except sqlite3.IntegrityError:
      return False
  ```

#### [ISSUE-HIGH-03] `is_duplicate` 仅凭（销售方+金额）判定重复，导致同金额合法发票被误判拦截
- **严重级别**: 🟠 High
- **文件路径**: `scripts/invoice_fetch/db.py`
- **行号范围**: L440 - L465
- **所属类别**: 业务逻辑 / 数据完整性
- **技术分析 & 影响**:
  在 `InvoiceDB.is_duplicate` 中包含如下分支：
  ```python
  if seller_name and total_amount:
      row = self._conn.execute(
          f"SELECT 1 FROM invoices WHERE total_amount = ? AND seller_name = ?{cond}",
          (total_amount, seller_name),
      ).fetchone()
      if row is not None:
          return True
  ```
  在发票号码缺失（如非标电子凭证、出租车发票或 OCR 暂未提取发票号）的场景下，或者同一个月内向同一销售方开具的多笔相同固定金额发票（例如每月固定 30.00 元话费发票、同一天两笔 25.00 元餐饮发票），只要第二张发票的 `seller_name` 与 `total_amount` 匹配，就会被判定为重复发票而被直接丢弃或跳过入库。
- **推荐修复方案**:
  必须依据表唯一约束 `UNIQUE(invoice_number, total_amount, seller_name)` 进行去重。对于无发票号的凭据，必须结合开票日期 (`expense_date`/`invoice_date`)、文件 SHA-256 哈希 (`file_hash`) 或邮件 UID 复合判定：
  ```python
  if invoice_number and total_amount and seller_name:
      row = self._conn.execute(
          f"SELECT 1 FROM invoices WHERE invoice_number = ? AND total_amount = ? AND seller_name = ?{cond}",
          (invoice_number, total_amount, seller_name),
      ).fetchone()
      return row is not None
  ```

#### [ISSUE-HIGH-04] GUI 主线程执行同步 IMAP 网络与 HTTP 下载，导致界面假死
- **严重级别**: 🟠 High
- **文件路径**: `scripts/invoice_fetch/gui/app.py`
- **行号范围**: L6600 - L6780 (`_redownload_selected_invoices`)
- **所属类别**: Qt GUI / 响应性能 / 架构分层
- **技术分析 & 影响**:
  用户在界面表格中选中发票并点击“重新下载”时，`_redownload_selected_invoices` 方法直接在 Qt GUI 主线程中：
  1. 通过 `MailFetcher` 建立与远程 IMAP 服务器的 TLS 连接（L6647-L6655）；
  2. 通过 `LinkDownloader` 同步请求远程 HTTP 下载链接并等待响应（L6674）；
  3. 同步调用 `parser.parse_pdf` 进行 PDF 文本解析；
  4. 期间使用 `QApplication.processEvents()`（L6659）试图刷新界面。
  若网络延迟高或 IMAP 超时（默认 10~30s），GUI 瞬间冻结并出现 Windows“（未响应）”白屏；`processEvents()` 极易引起鼠标二次点击、菜单重入和状态机混乱。
- **推荐修复方案**:
  将批量重新下载与解析逻辑抽取为独立的 `RedownloadInvoicesWorker(QThread)`，通过 Qt 信号槽将进度与结果传回主线程。

- **严重级别**: 🟠 High

#### [ISSUE-HIGH-06] `__main__.py` 跨模块直接篡改 `services.py` 私有全局变量 `_rename_source_mode`
- **严重级别**: 🟠 High
- **文件路径**:
  - `scripts/invoice_fetch/__main__.py`: L1079 - L1080, L1168
  - `scripts/invoice_fetch/services.py`: L195, L246
- **所属类别**: 架构设计 / 模块耦合 / 线程安全
- **技术分析 & 影响**:
  在 `__main__.py` 的 `_reprocess_email_records` 中，为了在重新处理时降低文件名冲突日志级别，代码直接写道：
  ```python
  # __main__.py:1079-1080
  prev_rename_mode = application_services._rename_source_mode
  application_services._rename_source_mode = "reprocess"
  ...
  # __main__.py:1168
  application_services._rename_source_mode = prev_rename_mode
  ```

## 4. 架构评估与重构路线图 (Architecture & Refactoring Roadmap)

### 4.1 `__main__.py` → `services.py` 拆分现状评估
本次拉取的重构成功将邮件下载、发票解析等基础操作从 `__main__.py` 剥离，方向正确。但目前的拆分仍属于**“半成品过渡态”**：
1. **职责倒挂**：`__main__.py` 依然持有 `_cmd_evidence_repair` 和 `_reprocess_email_records` 两个大型业务领域函数（共 400+ 行）；
2. **私有依赖侵入**：`__main__.py` 从 `services.py` 导入了 10 个 `_` 私有函数，构成了事实上的深层内部耦合；
3. **全局状态污染**：通过 `_rename_source_mode` 穿透修改服务层内部状态。

### 4.2 `services.py` 模块化子包重构设计
建议将 4,127 行的 `services.py` 单体解耦为高内聚、低耦合的领域服务子包：

```
scripts/invoice_fetch/services/
├── __init__.py                # 统一公共导出 API，保障向下兼容
├── mail_scan_service.py       # 邮箱并发连接、UID 扫描与邮件拉取流水线
├── local_import_service.py    # 本地文件目录/ZIP 遍历、魔数嗅探与入库
├── evidence_match_service.py  # 报销材料、行程单、水单启发式关联打分算法
├── invoice_classifier.py      # 发票类型、费用科目、币种纯函数分类器
├── repair_service.py          # 从 __main__.py 迁入的证据修复与邮件重检核心业务
└── file_naming_service.py     # 发票重命名规则与冲突解决策略（含 ContextVar 上下文）
```

### 4.3 PySide6 GUI 架构治理规范
1. **统一 Worker 注册与生命周期看门狗**：
   在 `InvoiceReviewApp` 中引入 `WorkerRegistry`，所有异步任务必须通过注册器启动。`closeEvent` 统一通过注册器执行广播取消与协同 `wait(timeout)`，超时后安全释放资源。
2. **零主线程 I/O 原则**：
   彻底杜绝在 GUI 主线程中执行 `MailFetcher.connect()`、`LinkDownloader.download()` 以及 `parser.parse_pdf()`。所有耗时 >50ms 的操作必须封装为 `QRunnable` 或 `QThread`，严禁使用 `QApplication.processEvents()` 缓解阻塞。
3. **解耦 24 个后置补丁流水线**：
   制定 3 个迭代周期，将 `review_baseline_pipeline` 和 `settings_baseline_pipeline` 中分散在 24 个冻结模块的样式修复与控件调整，回填并直接固化至 `ReviewPage` 与 `SettingsDialog` 的主构建方法中，最终废弃延迟补丁机制。

## 5. 数据库与安全专项评估 (Database & Security Assessment)

### 5.1 SQLite 事务边界与 WAL 并发安全
1. **显式事务边界**：严格弃用隐式事务捕获后裸 `return False` 的模式。所有包含多条 SQL 或涉及业务一致性的操作均采用 `with self._conn:` 保证原子性与自动回滚。
2. **连接隔离与外键支持**：
   - 保证每个工作线程持有独立的 `InvoiceDB` 实例或使用线程局部存储（Thread-Local Connection）；
   - 在连接建立的第一时间强制执行 `PRAGMA foreign_keys = ON;` 与 `PRAGMA busy_timeout = 30000;`；
   - 对批量操作强制采用分块查询（`CHUNK_SIZE = 500`），消除 SQLite 参数超限隐患。

### 5.2 纵深安全防御机制 (Defense-in-Depth)
1. **Excel 导出全量转义**：对所有写入 Excel 单元格的字符串，不论是否在异常表，必须强制通过 `_safe_excel_value` 过滤首字符（`=`, `+`, `-`, `@`）。
2. **日志脱敏全局覆盖**：将 `PrivacyLogFilter` 挂载到根 logger `scripts.invoice_fetch`，覆盖数据库、迁移和导出所有底层模块。
3. **凭据安全与异常体系**：在 `credentials.py` 中建立结构化异常树（`InvoiceHubError` -> `CredentialError`），杜绝在底层基础库中调用 `SystemExit`。

## 7. 结论 (Conclusion)

Invoice Hub 具备坚实的架构设计与严谨的安全防御基础。本次拉取的重构迈出了关键分层的第一步，但在并发安全、主线程响应性、CI 门禁完整性与重构一致性上留下了若干高优先级问题。遵循本报告的 41 项问题清单与三阶段整改路线图，团队可在 1~2 个迭代内彻底消除核心风险，实现稳定、高可用且易于维护的生产级桌面发票管理平台。
