## 1. Exact root cause and wait owner

`PERF-SHUTDOWN-001` was confirmed as a Windows Firewall status-query wait,
not a SQLite close wait and not an HTTP-server shutdown wait on the idle path.

The blocking chain was:

1. `InvoiceReviewApp.closeEvent()` synchronously called the mobile controller
   shutdown path.
2. `MobileUploadSessionController.stop()` refreshed formal and development
   firewall status even while the application was closing.
3. The resulting `stopped` signal caused the mobile panel to enter its idle
   state, which refreshed firewall status a second time.
4. Each firewall query launches the hidden PowerShell query with an 8-second
   subprocess timeout. On the observed Windows machine, the actual query
   commonly took about 5--6 seconds.

This explains the stable 11--12 second fresh-idle close time: two sequential
firewall queries were on the GUI close path. The measured SQLite API call was
sub-millisecond, so the old GUI stall label around `db_close` was an upstream
stage-labeling error rather than database evidence.

The unique idle wait owner is therefore the duplicate firewall diagnostics
refresh during synchronous application shutdown.

## 3. Instrumentation and implementation

The opt-in performance probe now has a scoped `performance_stage()` helper.
When performance mode is disabled it performs no clock read and emits no
stage event. When enabled it records begin/end, elapsed milliseconds, thread
identity, active state, and timeout metadata.

Shutdown instrumentation covers:

- mobile controller/session shutdown and start-thread wait;
- HTTP server `shutdown()`, `server_close()`, and conditional server-thread
  join;
- mobile status timer stop;
- mailbox cancellation/wait and migration wait;
- settings flush;
- the actual `sqlite_close_call()` API invocation;
- close-event acceptance and window-hide scheduling.

The behavioral fix is intentionally narrow:

- a shutdown with no starting thread, server, or session takes the inactive
  fast path and does not query the firewall;
- the active shutdown path stops the server without refreshing firewall
  diagnostics;
- the stopped/expired panel state suppresses a diagnostic refresh while the
  application is closing;
- server shutdown joins only an actually live server thread, with a bounded
  two-second protection timeout;
- no product path uses `terminate()`, `kill()`, or `os._exit()` to force
  shutdown.

The startup and ordinary user-triggered firewall status refresh remains
unchanged; it is outside this shutdown fix and is reported as a remaining
diagnostic cost below.

### Follow-up: PERF-SHUTDOWN-002

`migration_worker.wait()` and the mailbox scan worker's `wait()` remain
unbounded waits in the pre-existing shutdown path. They were intentionally not
changed in Phase 2A. `PERF-SHUTDOWN-002` remains `OPEN / NOT REPRODUCED` and
requires a separate boundedness investigation with native evidence before any
implementation change.

## 5. Real HTTP upload-completed shutdown gate

Android is not required for Phase 2A. Android physical-device validation remains
the right evidence for QR scanning UX, mobile browser layout/gesture, and
Wi-Fi/LAN reachability, but those are outside this shutdown optimization scope.

The following runs used the normal visible Windows Qt application, a normal
mobile upload server session, a generated upload URL/token, and a headed desktop
Chromium browser. The browser selected in-memory synthetic PDF files and posted
multipart form data to the generated URL. No direct completion callback or
mocked import was used. Tokens and full URLs are intentionally omitted from
this report.

Each run kept the same mobile server/session alive, completed batch A, then

The Phase 2A shutdown behavior is server/client-device independent. A native

## 7. Database and data-safety evidence

After the observational runs:

- SQLite `PRAGMA integrity_check` returned `ok`;
- the HTTP-upload runtime database remained readable with 12 invoice rows;
- all 12 HTTP-upload rows retained `review_status=to_review`;
- settings remained readable after restart;
- the HTTP path accepted all A/B/C batches without a partial-failure result;
- duplicate batches did not create extra rows for the duplicate file;
- the latest batch scope remained the latest GUI handoff after two sequential
  batches in one session;
- no residual InvoiceHub or benchmark wrapper process remained;
- all recorded HTTP lifecycle runs reached process exit;
- repeated visible start/close runs did not leave an orphan server or worker.

The fix does not force-kill a worker or process and does not alter SQLite
pragmas or transaction semantics.

## 8. Remaining stages over 100 ms

- Active HTTP server shutdown is the only normal shutdown stage observed in
  the hundreds-of-milliseconds range: approximately 307--490 ms.
- Settings flush was approximately 10--32 ms in the observed runs.
- Actual SQLite close was below 1 ms.
- The 5--6 second firewall query remains a startup/ordinary diagnostics cost,
  but no longer runs unconditionally during application close.

There is no evidence that database close, WAL checkpointing, or a database
lock owns the former 10--12 second idle wait.
