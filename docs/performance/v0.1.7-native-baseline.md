## Executive verdict

| Area | Verdict | Evidence boundary |
| --- | --- | --- |
| Mobile completion native baseline | **BLOCKED** | No physical Android device was available in this run; `_mobile_upload_finished` was not exercised by a real upload. |
| Page switch native baseline | **PASS** | 20 visible-Qt cycles in each instrumentation mode; current 17-row runtime. The 250-row case remains unavailable. |
| PDF preview native baseline | **NEEDS WORK** | Warm one-page previews are fast, but cold first paint approached 500 ms and the source-launcher run produced a native Windows access-violation dialog. Multi-page and large-PDF cases were unavailable. |

| User symptom reproduction | **PARTIAL** | Exit delay was reproduced. Page-switch delay was not reproduced in the measured native path; mobile completion and the synthetic 1839 ms preview tail were not reproduced. |
| Phase 2 optimization targets | **EVIDENCE-BASED** | Shutdown investigation is supported by native evidence. Completion deduplication and broad preview/page-switch changes remain gated on missing real-device or representative-file evidence. |

This is a reality-validation report, not a claim that every requested native
scenario passed. The unavailable cases are recorded explicitly rather than
replaced with synthetic data.

## 2. Instrumentation overhead gate

The same visible page-switch and PDF interaction loops were run with
`INVOICE_HUB_PERFORMANCE=1` and with it disabled. The external timing includes
the visible-Qt action round trip and a fixed settling delay, so it is an
overhead comparison, not a pure application latency measurement.

### Page switch, 80 transitions per mode

| Mode | Median | P95 | Max | Samples |
| --- | ---: | ---: | ---: | ---: |
| PERF enabled | 519.87 ms | 576.75 ms | 595.84 ms | 80 |
| PERF disabled | 521.50 ms | 561.81 ms | 709.75 ms | 80 |
| Enabled delta | -0.31% | +2.66% | — | — |

The +2.66% P95 difference is within the visible automation/settling noise
observed in this harness; the median moved in the opposite direction. The
structured application trace available in enabled mode was much smaller:
last 80 logged page traces had median 37 ms, P95 52 ms, and maximum 58 ms.
Accordingly the page-switch overhead gate is **PASS within measurement noise**,
with a note that a strict sub-2% P95 assertion would require a lower-noise
native profiler harness.

### PDF preview, 20 row clicks per mode

| Mode | Median | P95 | Max | Samples |
| --- | ---: | ---: | ---: | ---: |
| PERF enabled | 1,072.98 ms | 1,096.98 ms | 1,106.66 ms | 20 |
| PERF disabled | 1,071.12 ms | 1,120.77 ms | 1,156.07 ms | 20 |
| Enabled delta | +0.17% | -2.12% | — | — |

These values include an 850 ms post-click settle used to allow the visible
preview to become stable. They show no measurable instrumentation regression.

The disabled path does not install `PerformancePaintObserver` or
`GuiStallDetector`, and does not emit opt-in structured traces. A small amount
of always-on timing remains in `_load_invoices()` (`time.perf_counter()` around
database/filter/render sections), which is existing timing instrumentation and
was not expanded in this phase. It should be removed or gated only as a
separate, measured cleanup if future profiling shows it matters.

## 3. Native mobile-upload completion

**Status: BLOCKED.** No real Android phone was available, so the required
10–20 real upload rounds could not be performed. There is no valid native
evidence in this run for:

- scan/upload/import completion timing;
- `task_done_to_first_paint` or `task_done_to_interactive` after a real upload;
- `_mobile_upload_finished` stage call graph;
- `_load_invoices()` call count per real upload batch;
- duplicate completion refresh cost;
- automatic handoff to the review page after a real phone upload.

The Phase 1 synthetic report still identifies the suspected second
`_load_invoices()` during review handoff, but this report does not promote that
synthetic suspicion to a native optimization target. A phone and a controlled
real upload batch are the resume gate.

## 4. Native local import and mailbox completion

**Status: BLOCKED for completion timing.** The visible application was started
normally, but no mutating local import or real mailbox scan was run against the
user runtime during this observation pass. This avoids changing the user's
records while no deterministic isolated acceptance dataset was available.

Consequently this run does not claim native `worker_finished` to useful-paint
measurements, nor does it claim whether `QMessageBox` or refreshes of overview,
imports, settings, and invoice list block the completion path. A future run
needs either an explicitly disposable local dataset or a real mailbox test
window.

## 5. Native PDF preview

### Warm one-page PDF sample

Two real one-page PDFs from the project runtime were alternated for 20 visible
row selections. The controlled enabled-mode application traces were:

| Stage | Median | P95 | Max |
| --- | ---: | ---: | ---: |
| Total | 50 ms | 68 ms | 72 ms |
| Load requested | 4 ms | 7 ms | 8 ms |
| Document ready | 11 ms | 12 ms | 12 ms |
| First paint | 20 ms | 31 ms | 45 ms |
| Interactive | 15 ms | 19 ms | 21 ms |

The loop generated 20 controlled preview traces for 20 row clicks; no same-
click duplicate preview load/render was observed. There was one separate cold
startup preview trace with total approximately 497 ms:

```text
load_requested=19ms
document_ready=113ms
first_paint=310ms
interactive=55ms
```

No controlled visible sample exceeded 1,000 ms, so `PERF-PREVIEW-SPIKE` was not
reproduced. The cold first-paint result is still materially slower than the
warm path and merits targeted follow-up if representative PDFs reproduce it.

### Missing file classes

The runtime inventory contained no valid multi-page PDF and no valid PDF above
1 MB. Multi-page navigation, large-file decode, and their stage breakdown are
therefore **BLOCKED/NOT REPRODUCED**. No synthetic replacement was introduced.

One normal source-launcher run also produced a native Windows
`python.exe - 应用程序错误` access-violation dialog after visible startup and
initial preview activity. The newly packaged visible run did not reproduce that
dialog during the controlled warm preview loop. This is native stability
evidence to retain for follow-up, not a root-cause claim and not a reason to
change preview code in this phase.

## 6. Native page switching

The visible loop covered 20 cycles of:

```text
Overview -> Review -> Imports -> Review -> Overview
```

That is 80 transitions in each instrumentation mode. The enabled structured
application traces for the last 80 records were:

| Destination | Count | Median | P95 | Max |
| --- | ---: | ---: | ---: | ---: |
| All recorded page traces | 80 | 37 ms | 52 ms | 58 ms |
| Overview | 32 | 45 ms | 55 ms | 58 ms |
| Review | 32 | 36 ms | 41 ms | 42 ms |
| Imports | 16 | 28 ms | 33 ms | 33 ms |

Database/filter work in the trace was generally 0–7 ms; first-paint and
interactive markers accounted for the remainder. This native sample does not
support attributing the Phase 1 synthetic 296 ms P95 to page activation or
synchronous refresh. It supports keeping page switching below the current
Phase 2 priority list until a larger real dataset is measured.

The requested 250-row refresh was not run because the available user runtime
has 17 rows and no disposable 250-row dataset was authorized. The 250-row
native gate is **BLOCKED**, not passed by extrapolation.

## 7. Native shutdown

### Fresh idle, ten visible runs

These runs launched the current packaged executable normally, waited for the
visible window, sent a normal close request, and polled until the process was
gone. The default user runtime was used for the empty-idle condition.

| Metric | Result |
| --- | ---: |
| Samples | 10 |
| `close_to_hidden` minimum | 11,639 ms |
| `close_to_hidden` median | 11,739 ms |
| `close_to_hidden` P95 | 12,637 ms |
| `close_to_hidden` maximum | 12,637 ms |
| `hidden_to_exit` | 0 ms at polling resolution in all samples |

The individual close-to-hidden values were 11,639, 11,658, 11,720, 11,720,
11,739, 11,851, 11,863, 11,956, 12,490, and 12,637 ms.

### PDF-loaded trace evidence

Two controlled visible runs with the project runtime and a PDF-loaded review
surface emitted the product's structured shutdown traces:

| Trace | Total | Mobile shutdown | Window hidden | Stall source |
| --- | ---: | ---: | ---: | --- |
| Native run 1 | 10,804 ms | 10,741 ms | 51 ms | `db_close` 10,804.807 ms |
| Native run 2 | 11,429 ms | 11,351 ms | 59 ms | `db_close` 11,464.369 ms |

The trace ordering is:

```text
close_requested
 -> mobile_shutdown
 -> migration_wait / scan_cancel_wait
 -> db_close
 -> close_event_accepted
 -> deferred window hide
```

The dominant wait occurs before the window is hidden, not in the final process
poll. This is sufficient native evidence for a Phase 2 shutdown investigation.

The following requested states were not run and remain blocked: active mobile
upload service, immediately after a real mobile upload/review handoff, and
5–10 minutes of real user operation. Fresh idle was completed; PDF-loaded
shutdown has two traces but not ten repetitions, so it is evidence rather than
a completed per-state acceptance gate.

## 9. Ranked Phase 2 targets

Only the first target is currently supported by native evidence:

1. **Shutdown lifecycle / `mobile_shutdown` / `db_close`** — create a separate
   before/after investigation PR. Split mobile server stop, worker waits,
   database close, and deferred window hide with a native trace. Do not change
   semantics until the wait owner is identified.
2. **Cold PDF first paint** — only investigate after obtaining representative
   multi-page and larger real PDFs in a disposable test runtime. Keep decode,
   render, and paint separate.
3. **Mobile completion refresh deduplication** — blocked until a real phone
   upload captures `_mobile_upload_finished`, both `_load_invoices()` calls,
   and the review-scope handoff. The synthetic call graph is not sufficient.
4. **Page-switch optimization** — do not prioritize from this run. Native page
   traces are fast; remeasure with a real 250-row disposable dataset before
   proposing a change.

No Phase 2 implementation is included in this branch.
