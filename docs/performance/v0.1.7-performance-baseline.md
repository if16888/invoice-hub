# Invoice Hub v0.1.7 Performance Baseline

Status: Phase 1 observability and benchmark only

Baseline branch: `perf/v017-performance-baseline`

Baseline source: `master` at `50855c7edb6e04532fe298b6ec9c4adcb20fb990`

Stable boundary: v0.1.6 remains frozen; this work does not modify the v0.1.6 tag, release, or assets.

## Scope

This phase adds opt-in GUI performance traces, first-paint markers, completion checkpoints, a GUI stall detector, and a deterministic synthetic benchmark. It does not change invoice, upload, mailbox, review, preview, or shutdown semantics. No optimization, caching, async conversion, schema change, or UI redesign is included.

The observation points cover:

- mobile upload, local import, and mailbox completion callbacks;
- invoice list refresh stages and page switches;
- review actions and PDF preview request/render/first-paint paths;
- close/shutdown phases and deferred window hide.

Performance mode is opt-in through `INVOICE_HUB_PERFORMANCE=1`. Sensitive paths, URLs, filenames, invoice fields, mailbox values, credentials, and tokens are redacted before they reach the performance log sink.

## Measurement method

The baseline was generated on 2026-08-24 with 20 repetitions for every scenario:

| Field | Value |
| --- | --- |
| OS | Windows-10-10.0.26200-SP0 |
| Python | 3.11.9 |
| Qt platform | `offscreen` |
| Data | synthetic only |
| Repetitions | 20 per scenario |
| Timing clock | `time.perf_counter()` / monotonic elapsed time |
| Raw result | `dist/performance/v017-baseline-20260824.json` |

The offscreen run is a deterministic code-path baseline, not native Windows visual acceptance and not real mailbox, LAN phone, or production-database evidence. Native GUI and real-device measurements remain a separate follow-up gate.

## Observed symptoms and hotspots

The synthetic data points to three areas for Phase 2 diagnosis:

1. **Consecutive mobile completion is the clearest completion-path outlier.** The A→B scenario has a P95 of 408.427 ms. The completion trace across all mobile cases has P95 427.980 ms and maximum 628.783 ms.
2. **The completion/page-paint path has wider tail latency than the direct scenario timings.** The page-switch trace has P95 296.091 ms and maximum 507.995 ms. The preview trace has P95 179.813 ms and maximum 1839.373 ms, so the rare preview tail must be investigated with a real PDF and native paint evidence before changing implementation.
3. **The 1000-row list is not the dominant synthetic cost in this run.** Its P95 is 54.599 ms and maximum 63.713 ms, but the stage trace is retained so DB, filtering, item allocation/population, sorting, selection restoration, detail binding, preview trigger, and layout scheduling can be compared in later runs.

The current instrumentation reports each completion checkpoint as T0–T6:

| Marker | Meaning |
| --- | --- |
| T0 | Worker/controller work completed |
| T1 | GUI completion signal entered |
| T2 | GUI state update completed |
| T3 | Database/list refresh completed |
| T4 | Page switch requested |
| T5 | First paint observed/scheduled for the target surface |
| T6 | Interactive continuation scheduled after paint |

`function return` is not treated as paint completion. The paint observer attaches to the Overview, Review, Imports, and Preview surfaces and emits the first-paint/interactive markers on the Qt event loop.

## List-refresh stage contract

`[性能][列表刷新]` keeps separate stage timings for DB query, scope/filter, model transformation, table clear, row allocation, `QTableWidgetItem` creation/cell population, sorting state, selection restoration, detail binding, preview trigger, and layout scheduling. Existing sorting behavior is not changed; the trace records whether sorting was enabled at the observation point.

## Suspected redundant refresh

The mobile completion call graph is currently:

```text
mobile worker/controller done (T0)
  -> _mobile_upload_finished (T1)
  -> import activity/state update (T2)
  -> _load_invoices / _load_claims / overview/import/settings refresh (T3)
  -> _open_import_activity_review
       -> _load_invoices again when review handoff opens
       -> _switch_main_page (T4)
  -> target surface first paint (T5)
  -> interactive continuation (T6)
```

The second `_load_invoices()` is recorded as a suspected redundant refresh; this phase intentionally does not remove or coalesce it. Phase 2 should compare its trace cost against the handoff requirement and verify stale-scope behavior before any change.

## GUI stall detector

The opt-in event-loop detector samples a monotonic heartbeat and records gaps above 50 ms, 100 ms, and 300 ms with the active stage label. Across the complete synthetic run it recorded 414 gaps, P95 1440.143 ms, and maximum 1771.256 ms. The current aggregate stage labels are `event_loop` (329) and `db_close` (85). These values are diagnostic signals, not a root-cause claim: the benchmark includes repeated offscreen window construction/teardown and must be reproduced with native Windows timing before attributing the gaps to the product path.

## Shutdown path

The observed close path is:

```text
close requested
  -> mobile upload shutdown
  -> migration wait
  -> mailbox scan cancel/wait
  -> preferences/database close
  -> closeEvent accepted
  -> deferred window hide
```

In the synthetic baseline, all P7 cases remain below the stated 1,000 ms idle-exit and 2,000 ms mobile-shutdown ceilings. This is not a substitute for native Windows exit evidence, especially with a real active server, PDF renderer, mailbox worker, or representative user database.

## Phase 2 plan

No Phase 2 implementation is included in this branch. The next investigation should:

1. capture the same traces on native Windows with a visible Qt platform and a representative database;
2. compare T0→T3 versus T3→T6 for mobile, local-import, and mailbox completion;
3. validate whether the second review-handoff list load is redundant or required for scope correctness;
4. split PDF preview first-paint latency by file size/page count and distinguish PDF decode from Qt paint scheduling;
5. isolate `db_close` and event-loop stalls during shutdown without changing normal shutdown semantics;
6. only then propose narrowly scoped optimization patches with before/after evidence.

## Gate interpretation

This report establishes the v0.1.7 Phase 1 measurement baseline. It does not claim that all GUI performance targets are met in native use, and it does not close a performance issue based only on synthetic/offscreen timing. The repository test, compile, privacy, public-export, and diff gates are recorded with the commit that carries this instrumentation.
