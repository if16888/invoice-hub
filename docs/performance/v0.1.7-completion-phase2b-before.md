## 1. Scope and data boundary

This phase is limited to completion-to-result UI latency:

```text
authoritative worker/import completion (T0)
  -> GUI signal (T1)
  -> state update (T2)
  -> list/data refresh (T3)
  -> page handoff (T4)
  -> first useful paint (T5)
  -> interactive (T6)
```

No shutdown, PDF architecture, ordinary page switching, database schema,
parser, deduplication semantics, firewall, or native geometry implementation
was changed.

An onedir package was built into a new ignored Phase 2B output directory from
the branch during the launch investigation. The final worker/server marker
changes were added after that package was built, so the package was not used
as source-matched native evidence and must be rebuilt before resuming the
native gate. No release artifact, stable tag, user invoice, credential,
mailbox value, or PDF content was added to the repository.

## 2. Observation changes

The following changes are observation-only:

- Local-import and email workers carry a private monotonic completion marker on
  their GUI signal payload.
- The mobile server records the private marker at authoritative batch
  finalization; the marker is projected out of the public HTTP result.
- The GUI completion trace can begin at that worker marker, so the first
  `T1_gui_signal` stage includes the worker-to-GUI delivery interval.
- Existing completion calls are measured with ordinal names such as
  `load_invoices_1` and `load_invoices_2`.
- Each measured call records elapsed time, target surface, and whether that
  surface was visible before the call.
- Existing callbacks are still called in the same order. No refresh is
  removed, deferred, or made asynchronous by this instrumentation.

The instrumentation remains opt-in through `INVOICE_HUB_PERFORMANCE=1` and
does not alter the public upload response.

## 3. Static completion call graph to validate natively

### Mobile HTTP completion

The current code path is:

```text
T0 server batch finalization
  -> upload_batch_completed GUI signal
  -> _mobile_upload_finished
  -> state/activity update
  -> _load_invoices       (#1)
  -> _load_claims
  -> _refresh_overview_page
  -> _refresh_imports_page
  -> _refresh_settings_page
  -> _open_import_activity_review
       -> review page handoff
       -> _load_invoices   (#2)
```

The second list load is still present intentionally. It is a **suspected
redundant refresh**, not a confirmed optimization target. The review-scope
installation and selection semantics must be measured before changing it.

For a zero-review mobile result, the existing import handoff can also invoke
the imports refresh from `_switch_main_page` after the explicit imports
refresh. This must be counted from the completion trace rather than inferred
from source alone.

### Local import completion

```text
T0 LocalImportWorker finished
  -> _import_local_finished
  -> state/activity update
  -> completion QMessageBox
  -> _load_invoices
  -> overview refresh
  -> imports refresh
  -> settings refresh
  -> first paint / interactive
```

The modal completion message is intentionally included in the observation
path because it currently precedes list refresh.

### Email scan completion

```text
T0 EmailScanWorker finished
  -> _scan_email_finished
  -> state/activity update
  -> optional failure-details QMessageBox
  -> _load_invoices
  -> first paint / interactive
```

The deterministic email case may use the real visible signal handler, but it
must not be described as an IMAP/network benchmark.
